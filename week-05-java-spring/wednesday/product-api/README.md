# Product API

A simple REST API for managing products, built with Java 21 and Spring Boot. Data is stored in memory, so no database is required.

## Tech stack

- Java 21
- Spring Boot 4.1.2 (Spring Web MVC)
- Maven (wrapper included)

## Project structure

```
src/main/java/com/example/productapi
├── controller   # REST endpoints (HTTP layer only)
├── service      # Business rules and validation
├── repository   # Storage abstraction + in-memory implementation
├── model        # Domain entity (Product)
├── dto          # Request and error response objects
└── exception    # Custom exceptions and global error handler
```

## Getting started

### Requirements

- JDK 21 (a newer JDK also works, since the project targets Java 21)

### Run the application

From the project root:

```bash
./mvnw spring-boot:run
```

On Windows:

```bash
mvnw.cmd spring-boot:run
```

You can also run the main class `ProductApiApplication` from your IDE.

The API is available at `http://localhost:8080`. To use another port, set `server.port` in `src/main/resources/application.properties`.

### Build

```bash
./mvnw clean package
```

## Data model

| Field   | Type       | Notes                         |
|---------|------------|-------------------------------|
| `id`    | Long       | Generated by the server       |
| `name`  | String     | Required, cannot be blank     |
| `price` | BigDecimal | Required, cannot be negative  |
| `stock` | Integer    | Required, cannot be negative  |

## Endpoints

| Method | Endpoint         | Description          | Success response |
|--------|------------------|----------------------|------------------|
| GET    | `/products`      | List all products    | `200 OK`         |
| GET    | `/products/{id}` | Get a product by id  | `200 OK`         |
| POST   | `/products`      | Create a product     | `201 Created`    |
| PUT    | `/products/{id}` | Update a product     | `200 OK`         |
| DELETE | `/products/{id}` | Delete a product     | `204 No Content` |

### Request body (POST and PUT)

```json
{
  "name": "Mechanical keyboard",
  "price": 59.99,
  "stock": 25
}
```

The `id` is never sent in the body: it is generated on creation and taken from the URL on update.

### Response body

```json
{
  "id": 1,
  "name": "Mechanical keyboard",
  "price": 59.99,
  "stock": 25
}
```

`POST` also returns a `Location` header pointing to the new resource (e.g. `http://localhost:8080/products/1`).

### Examples

```bash
# Create
curl -i -X POST http://localhost:8080/products \
  -H "Content-Type: application/json" \
  -d '{"name":"Mechanical keyboard","price":59.99,"stock":25}'

# List
curl -i http://localhost:8080/products

# Get one
curl -i http://localhost:8080/products/1

# Update
curl -i -X PUT http://localhost:8080/products/1 \
  -H "Content-Type: application/json" \
  -d '{"name":"RGB keyboard","price":69.90,"stock":10}'

# Delete
curl -i -X DELETE http://localhost:8080/products/1
```

## Validation and error handling

Business rules live in `ProductService`:

- `name` is required and cannot be blank.
- `price` is required and cannot be negative (zero is allowed).
- `stock` is required and cannot be negative.

All validation errors are collected and returned together. Errors share a single JSON format:

```json
{
  "timestamp": "2026-10-24T10:15:30.123Z",
  "status": 400,
  "error": "Bad Request",
  "messages": [
    "Name is required",
    "Price cannot be negative"
  ]
}
```

| Status | When                                                              |
|--------|-------------------------------------------------------------------|
| 400    | Invalid data, malformed or missing JSON body, non-numeric id      |
| 404    | Product not found (GET, PUT and DELETE by id)                     |

A `PUT` on a non-existent id returns `404`; it never creates a product.

## Limitations

- **In-memory storage**: all data is lost when the application restarts.
- **No persistence layer**: there is no database or JPA.
- **No pagination, filtering or sorting** on `GET /products` (results are ordered by id).
- **No authentication or authorization**: all endpoints are public.
- **Manual validation**: rules are written in the service instead of using Bean Validation annotations.
- **Unmapped framework errors**: `405 Method Not Allowed` and `415 Unsupported Media Type` use Spring's default format instead of the custom error format.
- **No duplicate detection**: several products can share the same name.
- **No API documentation tool** (such as OpenAPI/Swagger).
